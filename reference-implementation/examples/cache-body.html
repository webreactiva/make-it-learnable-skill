Why a cache sits in front of your database

Not "because it's faster". By the end you should be able to say what it is faster than, when it is slower, and what breaks when it is wrong.

Browserthe reader APIyour server Databasedisk + query planner Redisin memory

Someone opens a product page. From here everything downstream is invisible to them — they only experience the total.

Your API receives it. Parsing the request, checking auth, building the response: fast. Single-digit milliseconds. This is almost never the problem.

Then it asks the database. The query itself may be quick, but the round trip is not free: connection, network hop, query planning, reading pages that may not be in memory.

Do that on every request, for every visitor, for a row that changed last Tuesday.
An identical product page is requested 1,000 times in a minute and nothing about it changes. How many times does the database run that same query? Once — databases cache repeated queries 1,000 times Roughly 10 — the connection pool batches them 1,000 times. Databases do keep pages in memory, and the query will get faster after the first run. But "faster query" is not "no query": you still pay the connection, the network hop, the planner and the serialisation, 1,000 times. Connection pools reuse connections; they do not merge queries. Each request still issues its own.

The database has no idea that the answer it just computed is about to be asked for again. That is the gap a cache fills — not speed, repetition.

A cache is a small, fast store that remembers answers you already computed. Reading from memory over a local network is roughly two orders of magnitude cheaper than a disk-backed query.

If a product page takes to build from the database and from Redis, then at a hit rate of the average read costs — and you have taken of the traffic off the database entirely.

Drag the hit rate down to 20% and watch the average barely move. That is the thing people get wrong about caching: a cache with a poor hit rate is not a small win, it is nearly no win at all — while still costing you a whole new source of stale data.

A hit is boring. Every interesting bug in a caching layer lives on the miss path, because that is where two systems have to agree about what is true.

Note step 5: on a miss the cache made the request slower. Caching is a bet that misses are rare.

The question is never "is this slow to fetch". It is "what happens if I serve a version of this from five minutes ago". A stale country list is nothing. A stale stock count sells you something that does not exist. A stale basket belongs to someone else.

 This updates a product. One line makes the cache serve wrong data for the next five minutes. Which one?
async function updateProduct(id, data) { const product = await db.products.update(id, data) await redis.setex(`product:${id}`, 300, JSON.stringify(product)) await search.reindex(product) // may throw return product }

Nothing is wrong with the write order — the database changes first, then the cache. The problem is that reindex can throw after both have been written, so the caller sees a failure and retries or reports an error, while the cache is already holding the new value for 300 seconds. Your failure path and your cache now disagree about whether the update happened.

The fix is not reordering. It is deciding whether the cache write belongs inside the same failure boundary as everything else — usually by invalidating rather than writing through: await redis.del(`product:${id}`).

 Put a cache-aside read back in order. request arrives at the API look for the key in the cache on a miss, query the database write the result back with a TTL return the response

The name says it: the cache sits aside the database, and the application is what knows about both. Nothing in this sequence happens automatically — which is exactly why the invalidation is your problem and not Redis's.

Move the sliders until the cache stops being worth it. It happens sooner than most people expect.

 A cache is doing its job at a 90% hit rate. Hits cost 2 ms, misses cost 122 ms. What is the average read latency?

0.9 × 2 + 0.1 × 122 = 14 ms. The interesting part is that one request in ten is still slow — averages hide tails. If you only ever look at the mean, a cache makes a system look healthier than the slowest 10% of your users are experiencing. Watch p99, not the average.

 A colleague says: "we should cache everything, caching always makes things faster." Write the shortest reply that would actually change their mind. A low hit rate means you pay the cost and get almost none of the benefit Cached data goes stale — you trade correctness for latency On a miss the request is slower than it would have been You add a second system that can fail or disagree with the first

"Caching only helps when the same answer is asked for repeatedly. If the hit rate is low, every request pays the lookup and still goes to the database — you've made it slower and added a second system that can disagree with the first. The real question isn't speed, it's how long you're willing to serve an answer that's out of date."

Invalidation. Two workable strategies, and they are not interchangeable. TTL: accept staleness up to a fixed window; simple, and wrong for a bounded, predictable time. Explicit invalidation: delete the key whenever the underlying row changes; correct, and it fails the moment one write path forgets. Most teams start with TTL and add invalidation on the two or three keys where staleness actually costs money.

Key design. A poor hit rate is almost always keys that are too specific — a key including a user id, a timestamp, or a full query string means nearly every request is unique and the cache is just overhead. Cache the shared part, and compose the personal part on top of it.

Stampede. When a popular key expires, every in-flight request misses at once and they all hit the database in the same millisecond — often harder than having no cache at all. The fixes are a lock so one request refills while the others wait, or refreshing slightly before expiry.
