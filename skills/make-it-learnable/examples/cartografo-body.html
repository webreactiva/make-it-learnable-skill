Cómo está construido Cartógrafo

Un juego de geografía en TypeScript y Vite, sin framework de UI. 1.700 líneas repartidas en nueve módulos. Al terminar deberías poder abrir el repo, saber en qué fichero tocar y por qué el proyecto está partido así.

El repositorio tiene tres capas y un fichero de arranque:

src/
  main.ts            arranque, estado vivo y cableado
  ui/    screens.ts  components.ts  dom.ts
  game/  questions.ts  state.ts  normalize.ts  scoring.ts  types.ts
  data/  countries.json
De los cinco módulos de game/, ¿cuántos importan algo de ui/? Ninguno Solo state.ts, para poder repintar Casi todos: es JS vanilla, no hay framework que los separe Ninguno. Las flechas van en un solo sentido: ui/ → game/ → types. Es la intuición razonable —sin framework nadie te obliga a separar— pero aquí la separación es deliberada y se sostiene en los nueve ficheros. Es justo al revés: state.ts es el módulo más puro del proyecto. No sabe que existe una pantalla.

Esta es la decisión estructural que explica todo lo demás. game/ es lógica pura: recibe datos, devuelve datos, no toca el DOM ni window. ui/ sí toca el DOM, y para saber qué pintar importa los tipos y las funciones de game/.

La consecuencia práctica: los 48 tests del proyecto viven todos sobre game/ y ninguno necesita un navegador ni un DOM simulado. Si añades lógica y te ves importando algo de ui/, es señal de que esa lógica está en la capa equivocada.

main.ts son 101 líneas y es el único sitio con estado mutable: un let state: GameState. Todo lo demás es puro.

ui/ pinta. screens.ts son 259 líneas —el fichero más grande del proyecto—, components.ts construye trozos reutilizables y dom.ts son 35 líneas de utilidades sin ninguna dependencia.

game/ decide. Generar preguntas, avanzar el estado, normalizar texto y guardar récords. Ni una línea toca el DOM.

Y types.ts está en el fondo, sin importar nada. Es lo que permite que las dos capas hablen sin conocerse.

Los datos entran por main.ts como un JSON importado, no por game/. Por eso los tests pueden pasarle diez países de mentira.

Hay un único objeto de estado. Todas las funciones de game/state.ts lo reciben y devuelven uno nuevo; nadie lo muta.

export interface GameState {
  screen: Screen;
  config: GameConfig;
  questions: Question[];
  currentIndex: number;
  score: number;
  correctCount: number;
  wrongCount: number;
  answered: boolean;
  lastAnswerCorrect: boolean | null;
}

"start" | "question" | "summary". Es todo el enrutado que tiene el juego: Screens.render() hace un if/else if sobre este campo y no hay router ni URL.

El GameConfig del nivel, sacado de LEVEL_CONFIGS. Lleva el pool, cuántas preguntas, cuántos puntos vale cada una y qué tipos de pregunta se permiten.

La partida entera se genera de golpe al empezar y se guarda aquí. No se van creando sobre la marcha, así que currentIndex es un simple cursor sobre un array ya cerrado.

Bandera anti-doble-clic. recordAnswer en main.ts empieza con if (state.answered) return;, y sin eso podrías puntuar dos veces la misma pregunta.

boolean | null. El null no es pereza: distingue «todavía no ha respondido» de «respondió mal», que es lo que la pantalla necesita para saber si pinta feedback.

Tres contadores en vez de derivarlos de questions. Redundante a propósito: la pantalla de resumen los lee directamente sin recorrer nada.

El cableado se monta una sola vez, en main.ts: la UI recibe callbacks y nunca toca el estado por su cuenta.

const screens = new Screens(appRoot, {
  onStart:   (pool: Pool)      => startGame(pool),
  onAnswer:  (correct: boolean) => recordAnswer(correct),
  onNext:    ()                => advance(),
  onRestart: ()                => startGame(state.config.pool),
  onHome:    ()                => goHome(),
});
Ordena lo que ocurre desde que el jugador pulsa una opción correcta hasta que ve la siguiente pregunta. screens.ts detecta el clic en la opción llama al callback onAnswer(true) main.ts ejecuta recordAnswer y comprueba state.answered state.ts devuelve un GameState nuevo con la puntuación sumada el jugador pulsa «Siguiente» y se dispara onNext advance() llama a nextQuestion y luego a screens.render

Un solo sentido: la UI avisa hacia arriba, main.ts reemplaza el estado, y solo entonces se vuelve a pintar. La UI nunca escribe en state.

Con una excepción, y conviene conocerla antes de tocar nada. Esta es recordAnswer entera:

function recordAnswer(correct: boolean): void {
  if (state.answered) return;
  state = correct ? recordCorrect(state) : recordWrong(state);
  // Actualizar solo el contador de puntuación
  // en el header sin re-renderizar todo
  const scoreEl = document.querySelector(".score");
  if (scoreEl) {
    scoreEl.textContent = String(state.score);
  }
}
state = recordCorrect(state) no hay re-render querySelector('.score') render() llega después Una sola línea de esa función rompe el flujo unidireccional. Púlsala.
function recordAnswer(correct: boolean): void { if (state.answered) return; state = correct ? recordCorrect(state) : recordWrong(state); const scoreEl = document.querySelector(".score"); if (scoreEl) scoreEl.textContent = String(state.score); }

main.ts consulta el DOM directamente. En todo el resto del proyecto, pintar es trabajo de ui/ y ocurre dentro de screens.render(state); aquí se salta esa capa para no repintar la pantalla entera por un número.

Es un atajo consciente —el comentario lo dice— y funciona. Pero deja una trampa: si añades cualquier otra cosa que dependa de la puntuación —una barra de progreso, un aviso de récord—, no se actualizará, porque el único elemento que se refresca aquí es .score. Y si alguien renombra esa clase en el CSS, el marcador deja de subir sin que falle nada ni salte ningún test.

Al empezar un nivel se genera la partida completa. Tres decisiones seguidas: qué países entran, qué tipos de pregunta hay, y qué distractores acompañan a cada respuesta.

const pool = allCountries.filter((c) => poolRank(c.pool) <= poolRank(config.pool));

const distractors = sample(pool.filter((c) => c.cca2 !== answer?.cca2), 3);
const options = shuffle([answer, ...distractors]);

El pool es acumulativo: en difícil entran también los países de fácil y medio, porque poolRank los ordena 0, 1, 2 y el filtro es <=.

El reparto de tipos tiene un detalle que conviene mirar despacio. El plan pedía «50% + 50%» para el nivel medio, que son 15 preguntas:

/**
 * medium: 8 name-to-flag + 7 silhouette-to-name (15 total)
 */
const half  = Math.floor(total / 2);
const other = total - half;
Con total = 15, ¿qué reparto sale de ahí? 8 nombre→bandera y 7 silueta→nombre, como dice el comentario 7 nombre→bandera y 8 silueta→nombre 7 y 7, descartando la que sobra 7 y 8. El comentario de encima dice lo contrario. Es lo razonable: el comentario está pegado a la función y describe justo este reparto. Pero Math.floor(15 / 2) es 7, y ese 7 va al primer bucle. No se descarta nada: other = total - half recoge siempre el resto, así que suman 15.

El desempate cae del lado de las siluetas. El test lo fija con expect(n2f).toBe(7); // floor(15/2), así que código y test coinciden — y el comentario se quedó describiendo la intención original.

Es inofensivo para el jugador, pero es lo primero que te va a confundir si tocas esta función fiándote de lo que hay escrito encima.

En difícil, seis preguntas piden escribir el nombre del país. Compararlo con === sería inusable, así que ambos lados pasan por esta cadena:

export function normalizeName(input: string): string {
  return input
    .toLowerCase()
    .normalize("NFD")
    .replace(/[\u0300-\u036f]/gu, "")
    .trim()
    .replace(/^(el|la|los|las)\s+/i, "")
    .replace(/\s+/g, " ")
    .trim();
}

NFD descompone cada letra acentuada en letra base más marca diacrítica suelta, y el replace siguiente borra ese rango Unicode: así «España» y «Espana» acaban iguales.

El jugador escribe " El Salvador ", con espacios delante. ¿Qué devuelve? "el salvador" "salvador" " el salvador" "salvador" — el artículo desaparece y la respuesta se da por buena. Sería correcto si el trim() estuviera al final, que es donde el plan del proyecto lo colocaba.

Fíjate en que hay dos trim(), y el primero es el que importa. La expresión /^(el|la|los|las)\s+/ está anclada con ^: exige el artículo al principio exacto de la cadena.

Sin ese primer trim, la regex se encontraría " el salvador", el ancla toparía con dos espacios en lugar de con la «e», no casaría, y el jugador vería un fallo por haber pulsado la barra espaciadora de más.

El plan del proyecto ordenaba los pasos al revés —artículos antes del trim—. El código se desvió y acertó. Y ningún test cubre este caso concreto: normalize.test.ts prueba «La India» y prueba « Estados Unidos », pero nunca un artículo con espacios delante.

countries.json no está escrito a mano: lo genera scripts/generate-countries.ts a partir de los assets que hay en public/. La línea que decide el tamaño del juego es esta:

const available = flags.filter((c) => silhouettes.includes(c)).sort();

El dataset es la intersección entre las banderas y las siluetas disponibles: 271 banderas, 242 siluetas, 242 países jugables. El plan pedía 195 y la cabecera del propio script ya lo dice claro — hard (resto). El número no se eligió: se heredó de dos paquetes de assets, y por eso el nivel difícil pregunta también por territorios y dependencias.

Hay un fichero entero validando estos datos, tests/data.test.ts, y pasa. Estas son sus aserciones sobre el tamaño:

expect(countriesData.length).toBeGreaterThan(0);
expect(easy.length).toBeGreaterThanOrEqual(30);
expect(medium.length).toBeGreaterThanOrEqual(50);
expect(hard.length).toBeGreaterThan(0);
¿Cuál de ellas habría fallado cuando los 195 previstos se convirtieron en 242? La del total: toBeGreaterThan(0) La de hard La de medium, porque el acumulado se dispara Ninguna: son todas cotas inferiores Comprueba que el fichero no esté vacío. Con 195, con 242 o con 4.000 pasa igual. Otra vez toBeGreaterThan(0): mide que exista algo, no cuánto. toBeGreaterThanOrEqual pone suelo, nunca techo. Pasarse es justo lo que no vigila.

Las cuatro ponen un mínimo y dejan el máximo abierto, así que el dataset puede crecer sin límite sin encender una luz roja. Lo que sí comprueban, y es lo importante para trabajar aquí, es que todo país del JSON tenga sus dos SVG: si añades un país sin silueta, ese test falla.

La lección práctica al tocar este repo: los tests de datos garantizan integridad —nada roto, nada duplicado, ningún asset ausente— pero no tamaño. Si el número de países importa para tu cambio, tendrás que afirmarlo tú.
